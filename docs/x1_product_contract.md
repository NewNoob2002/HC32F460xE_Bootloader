# X1 产品契约与待确认项

依据：当前工程源码、现有 Boot 板级契约，以及旧仓库 `X1_Panel_dev` 的 Git 对象 `771d4ea0671ebd7069be20a816d6b890dbd98b5c`。旧代码只能证明历史实现，不能证明当前产品板或 Linux 行为。阶段定义见 [实施计划](x1_app_implementation_plan.md)。

## 当前可以实施的启动边界

- 此前用户确认 X1 V1.3、HC32F460JEUA；现已换接并完成V1.5基础实板HIL，同一BIN自动识别两方案，见 [V1.5记录](x1_v15_hil.md)。Cortex-M4F/hard-float、8 MHz晶振/200 MHz系统时钟沿用当前 Boot，并已有启动/采样实板证据；未取得完整原理图/BOM重新核对。
- X1 App 由 Boot 交接进入，向量表位于 `0x8000`，Flash 结束于 `0x7A000`，不含 ICG。App 验证继承的时钟，不在 PLL 正作为系统时钟时重写 PLL 配置。
- Boot 交接已关闭全局中断，停止 SysTick、禁用/清除 NVIC，并将 PA6 拉低、PB5 熄灭、PB3 保持。App 初始化自身状态、时基与看门狗后才打开全局中断。
- P1 沿用已记录的 PB3 保持、PA6 看门狗及 PB5 故障指示。初始化失败/异常保持电源、停止喂狗并驻留，供调试及外部看门狗恢复；P3 正常关机释放 PB3 后则继续喂狗，避免外部供电下因复位重新上电。
- 普通 App 软件复位仍进入 Boot 更新窗口。App 不写升级完成 token。P3 复位命令的响应读取和超时规则已由本轮用户确认，见下方规则。

## 面板协议历史字节布局

帧头为 `AA 44 18`，字节 3 为头长 20；ID 为字节 4–5 的小端整数，载荷长度为字节 12–13 的小端整数，发送者/消息类型为字节 16/17。CRC32 覆盖头与载荷，初值/终异或均为 `0xFFFFFFFF`，旧实现使用查表反射 CRC32，末尾四字节小端；旧查表CRC与真实Linux黄金请求已核对为IEEE反射多项式 `0xEDB88320`。响应发送者为 `0x03`，查询响应类型 `0x01`，设置响应类型 `0x03`。保留字段不能继承旧共享缓冲残留。

真实 Linux 已确认 `0x01/0x02` 为查询类型0、2字节请求载荷；`0x03` 为设置类型2、8字节请求载荷，首字节为0/1录制状态。它还发送计划之外的 `0x06/0x08` 等消息，尚不支持。此前HIL未捕获 `0x04/0x05`，见 [HIL记录](x1_hil_test_version.md)；本轮用户已确认0x05=1是Linux关机完成确认，0x04=1请求普通软件复位。设置消息至少1字节且首字节仅允许0/1；4/5的0值返回ACK=0，不执行动作。保留扩展载荷，不复刻旧越界读取。

| ID | 历史用途 | 响应载荷 / 总长 | 已观察到的字段 | 未确认项 |
|---|---|---|---|---|
| `0x01` | 信息查询 | 36 / 60 字节 | HW `[0,8)`、FW `[8,16)`、SOC `18:u16`、温度 `20:u16`、电压 `22:u16`、状态 `26:u8` | 请求长度、温度/电压单位、保留字段、采样无效编码 |
| `0x02` | 控制状态查询 | 8 / 32 字节 | 复位 `0:u8`、关机 `1:u8`、录制状态 `2:u8`、操作 `3:u8`、充电 `4:u8` | 完整读出只确认所带录制操作，不表示Linux完成关机；充电位仅为已知正在充电，未知时0，关机通知仍可发送 |
| `0x03` | 主机录制状态同步 | 2 / 26 字节 | 请求载荷 `0:u8`，响应 `0=1`为接受、0为拒绝 | 未确认本地操作优先；禁止录制期间拒绝同步为开始，网络字段未接入 |
| `0x04` | 复位 | 2 / 26 字节 | 请求载荷 `0=1`，响应 `0=1`为接受 | ACK完整读出才复位；5 s未读取消，保留未读ACK，迟读不复位；普通复位仍进入Boot更新窗口 |
| `0x05` | Linux 关机完成确认 | 2 / 26 字节 | 请求载荷 `0=1`，响应 `0=1`为接受 | 成功发布后开始8 s断电延时，受首次关机请求起20 s兜底约束；重复确认不延长 |

以下偏移均相对于载荷首字节。信息温度保留BQ原始0.1K，电压保留旧线缆整数伏特，内部保持mV；未取得Linux端单位消费源码。无效采样不返回正常信息；所有设置命令在成功发布响应后才执行副作用，响应忙/发布失败不执行。当前 P5 版本信息为 `X1-P5`，日志构建ID为 `x1-p5`；旧 P3/HIL 哈希不适用于新 App。

## 双版本识别与充电边界

用户已明确：V1.3为GPIO方案，V1.5及以后为MP2762方案，同一固件运行时识别。代码集中在 `app_battery.cpp`，无基于产品main的反向依赖，也不因运行时通信故障切换方案。

- `Unknown`：不配置旧充电GPIO；对MP 0x5C定点探测，ACK后读REG00/08/13校验保留位，选择MP方案。只有健康BQ读样本与连续三次明确MP地址NACK才选择GPIO方案；超时/总线异常/读失败保持未知。
- MP没有独立器件ID，识别依赖确认过的总线拓扑，不能绝对区分首次启动前完全失联的MP与不存在的MP；消除盲区需要识别电阻/GPIO或可靠出厂标识。硬件字符串 `V1.5` 代表方案，不表示可识别后续每个PCB版本。
- 两方案均使用有效且新鲜的BQ电池温度（约0至45°C）控制充电；读失败和6s陈旧不允许充电。正常采样3s、控制500ms，未知板型探测200ms；识别后锁定。
- GPIO：PA1和PB7均满足源检测后稳定1.5s，再按旧方案允许PA4使能/PB10选择3A；禁用时两者低。未初始化时不输出，不用单次芯片探测失败决定GPIO行为。
- MP：仅I2C配置/读取状态；先禁充，再设置预充门槛6.6V、预充840mA、快充1600mA，写后回读。依据MP2762A Rev1.1 pp32–36/42：旧880mA请求实际编码840mA，6.6V函数实际设置预充门槛而非满充电压。保留OTP满充/供电配置，不全寄存器复位；失联时禁用无法确认会记录诊断，不能称已硬件停充。

V1.3已有识别、采样、关闭输出与Linux读取证据；V1.5现已通过真实MP识别、配置写后回读、快充/BQ状态与约10分钟无显式暂停的轮询窗口。电气充电/插拔/受控温度保护仍待验收；调试阶段的恢复及PIN复位不作为正常窗口通过，见[V1.5实板记录](x1_v15_hil.md)。

## P3 已确认时长与状态转换

以下规则由本轮用户确认，已经软件实现；新镜像尚未烧录，不能据此视为实板验收完成。

- 电源键PA0高有效、功能键PA15低有效。复用旧工程MultiButton的C实现和MIT许可证；5 ms轮询、4 tick消抖（标称20 ms）、300 ms单双击窗口。主循环迟到会延后库窗口，不补跑虚构GPIO样本；2 s/8 s产品长按由实际毫秒差判定，每段连续按下只触发一次。
- 仅纯上电复位（保留的RMU标志恰为`RMU_FLAG_PWR_ON`）等待电源键连续2 s确认；App初始化时起10 s未确认则释放PB3进入仅充电驻留。复位标志会累积，混合标志及软件/引脚/看门狗复位直接运行。确认开机的同一段长按不触发关机。
- 运行中电源键连续2 s请求正常关机，功能键连续8 s立即强制释放PB3。关机请求停录制并通过0x02持续通知；读取通知只表示送达，不等于安全关机完成。
- 0x05=1表示Linux已完成关机。成功发布ACK后进入8 s断电延时；从最初关机请求起20 s兜底，取较早截止时间。重复按键/确认不延长等待。Linux在运行中主动发来完成确认也接受，并从该命令起计时。
- PB3释放后若MCU仍被外部供电，驻留并继续看门狗、通信与充电处理；不复位、不自动重新拉高PB3，不接受开始录制或软件复位。重新开机依赖新的硬件上电/复位流程。
- 0x04=1仅在Running接受；成功发布ACK后最多等待5 s，关联ACK完整读出且尚未到期才复位。到期取消复位并保留未读ACK；迟读不复位，新请求不能覆盖原ACK或延长截止时间。ResetReady期间也拒绝新副作用；强制关机可打断等待。
- 有效新鲜BQ样本且充电状态明确未充电时，SOC≤9%（包含0%）立即停录制并产生一次待上报操作，禁止本地/主机重新开始录制。持续180 s请求正常关机；样本无效/6 s陈旧、充电状态未知、正在充电或SOC恢复均清除计时。使用实际时间，不按LED调用次数累加。
- 运行时看门狗仍为1 ms高脉冲、3000 ms间隔；异常与正常关机的喂狗策略分别保持上述契约。SOC稳定20分钟补偿、范围和保存时机按已冻结的 [P5计划](x1_p5_plan.md) D1–D7 实现；面板/LED 使用补偿值，低电量策略保持 BQ 原始值。

## 参数区与升级隔离

当前公共地址契约保持不变：Metadata A 为 `[0x7A000,0x7C000)`，Metadata B 为 `[0x7C000,0x7E000)`，保留扇区为 `[0x7E000,0x80000)`。旧 `FLASH_OFFSET_ADDR=0x7A000` 禁止使用。

保留扇区已于2026-10-12正式分配为App参数区 `APP_PARAM_SECTOR_BASE/SIZE/END`（`Common/Inc/firmware_layout.h`，编译期检查不与App/Metadata重叠），存放X1 SOC补偿记录，格式与写入时机见 [P5计划](x1_p5_plan.md) D6/D7。B4 已实现 `app_param_store_load/save`：16 字节小端追加记录、全扇区扫描取最大有效序号、CRC/范围/保留字段校验、满后擦除验证与写后回读；Flash 失败返回 false，不确认已保存。半写记录不重用；单扇区擦除窗口掉电仍按 0 恢复。主机回归覆盖 Flash 失败与掉电恢复；B5 已接入启动加载（读取失败按 0 继续）与主循环保存窗口。仅 Running/Off 驻留、无未读响应、非看门狗高脉冲时尝试保存，成功才清除待保存状态；失败保留并最早 3 s 后重试。实板阻塞时序留给 B6。Boot升级执行代码把擦除/下载限制在App区域，主机回归断言升级擦除不越过 `APP_FLASH_END` 且拒绝下载到参数区。Flash BSP本身可操作物理Flash，参数存储调用方须自行限制在该区间。
